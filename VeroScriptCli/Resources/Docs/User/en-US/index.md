# Command-line tool

The command-line program is named `veroscript`. It can run scripts, compile-check without executing, evaluate source text, enter a REPL, start a DAP debugger, build packages, validate binding catalogs, and generate AOT source.

## Initialize a project

```sh
veroscript project init
veroscript project init --path "./MyProject"
veroscript build --path "./MyProject"
```

Initialization creates missing `veroscript-project.json` and `veroscript-build.json`
with version `0.1.1`, empty dependencies and a portable application target that
produces `app.vsapp`. A new build configuration also supplies a minimal `main.vs`
if absent. Existing regular files are reported as `Kept` and are never overwritten;
an existing build configuration retains its own entry policy. Directory and
symbolic-link conflicts at file destinations return an error. Re-running the
command fills missing configuration. `project --help` and `project init --help`
show usage without writing files.

Without `--path`, the project is the current working directory. Relative paths
use the command's starting directory; absolute paths and `--path=<directory>` are
supported, and missing directories are created. The directory name is normalized
to a valid lowercase ASCII project name, falling back to `my-project` if needed;
the directory itself is not renamed. Initialization is local and performs no
dependency installation or script execution. `veroscript.lock` is generated by
successful installation, and `.veroscript/` is created as needed by package
management. Build execution requires a CLI with build services. See the
[minimal project example](../../../Examples/Project/README.md).

## Command forms

```powershell
# Run a source script or application package
veroscript [options] hello.vs [args...]
veroscript [options] DemoApp.vsapp [args...]

# Check without executing
veroscript --check hello.vs

# Execute source text
veroscript -e 'print(1 + 2);'

# Enter the REPL
veroscript -i

# Generate C++17 AOT source (the default target)
veroscript aot hello.vs -o generated.cpp

# Generate standalone Python source
veroscript aot --target=python hello.vs -o generated.py

# Generate a deterministic C# source bundle
veroscript aot --target=csharp hello.vs --output-dir generated --bundle-name App

# Validate or format a binding catalog
veroscript bindings validate catalog.json
veroscript bindings format catalog.json -o formatted.json

# Inspect a package
veroscript package inspect DemoApp.vsapp
```

A `main` with `string[] args` receives arguments after the script path; the path itself is not included in `args`. A parameterless `main` ignores extra arguments. An `int main` return value becomes the process exit code; a normally completed `void main` returns success.

The CLI process exit code is the script's final result: the `int main` value is returned, `exit(n)` takes precedence, and `void main` or an `int main` that reaches its closing brace produces `0`. This differs from the embedding API's `FRunResult` semantics; an embed host should use `bSuccess` to decide whether the engine completed normally, then inspect `ExitCode` separately.

## Common options

| Option | Purpose |
| --- | --- |
| `-e <source>` / `--eval <source>` | Executes source text; cannot be combined with `-i`, `--check`, or watch mode. |
| `-i` / `--interactive` | Enters the REPL. |
| `--repl-strict` | Requires `-i`; exits non-zero when the last REPL input failed. |
| `-I <path>` / `--import-path <path>` | Appends a module search path; repeatable. |
| `--stdlib-path <path>` | Adds a standard-library search root. |
| `--implicit-import <file>` | Imports a file into every compiled source; repeatable. It does not edit the source or re-export declarations automatically. |
| `--no-circular-imports` | Rejects cyclic module dependencies; cycles are allowed by default. |
| `--allow-circular-imports` | Explicitly restores the default behavior of allowing cyclic module dependencies. |
| `--allow-project-wide-access` | Allows project-wide access to non-exported declarations; use sparingly. |
| `--binding-catalog <file>` | Loads host-binding catalogs; repeatable and merged. It is available for ordinary check/run modes, but not with `-e`, `-i`, or watch mode. |
| `-D name[=value]` / `--define name[=value]` | Defines an object-like macro or conditional-compilation symbol. |
| `--macro NAME(params)=body` | Defines a structured host-style function macro; `--predefined-macro` is a compatibility alias. |
| `--check` | Compiles and reports diagnostics without executing; cannot be combined with `-e`, `-i`, or watch mode. |
| `--lang <tag>` | Selects a diagnostic language resolvable from the loaded culture directories. The default resources are determined by the culture directories packaged with the distribution; custom catalog roots can provide more languages. |
| `-o <path>` / `--output <path>` | Output path for AOT or binding-catalog formatting. |
| `--output-dir <path>` | C# or Python AOT multi-file bundle directory. |
| `--bundle-name <name>` | Portable source-bundle stem; the input stem is used when omitted. |
| `--manifest <path>` | C# bundle manifest path; the output directory is used when omitted. |
| `--target <name>` | AOT target: `cpp` (default), `csharp`, or `python`. |
| `-h` / `--help` / `-?` | Shows help. |
| `--version` | Shows the version, platform, and JIT capability information. |

## Execution backends and cache

| Option | Purpose |
| --- | --- |
| `--backend=vm` or `--backend vm` | Uses only the bytecode virtual machine. |
| `--backend=mixed` or `--backend mixed` | Uses JIT when supported and falls back to the VM; this is the default. |
| `--backend=jit` or `--backend jit` | Requires a compatible JIT module, selected explicitly or automatically by the module environment; eligible code is compiled eagerly, with VM fallback for unsupported bodies before entry. |
| `--bc-cache=off` / `--bc-cache=on` | Disables or enables `.vsbc` bytecode caching; enabled by default. |
| `--bc-cache-dir <path>` | Selects a shared bytecode-cache directory; the platform user cache is used when omitted. |
| `--vm-backend <id\|file\|directory>` / `--vm-backend=<id\|file\|directory>` | Selects the interpreter: shipped `vs-bytecode`, a compatible file/directory, or an installed backend ID when package support is available. Independent of execution policy. |

A complete Runtime supplies its matching interpreter in `Vm/`; keep that directory when deploying the CLI. `--vm-backend=vs-bytecode` selects that shipped backend. Other bare IDs are resolved only in the explicitly selected installed environment when package support is enabled; installation alone does not select them. File/directory paths are resolved from the startup directory and must match the Runtime. `--vm-backend` selects the interpreter, while `--backend=vm|mixed|jit` selects execution policy and `--jit-backend` selects a JIT implementation. Compilation that executes script processors also needs the selected interpreter; ordinary checking without such processors does not execute the entry script.

```sh
veroscript --vm-backend=vs-bytecode script.vs
veroscript --vm-backend=./custom-vm script.vs
```

Debugging uses the VM. `--watch` starts a fresh run with the selected execution policy whenever a watched file changes.

## Choosing a backend for performance work

The VM, mixed, and JIT-preferred backends implement the same language semantics. The mixed backend lets eligible hot code use the optimized tier while retaining VM fallback; the JIT-preferred backend asks for compilation more eagerly but is not a guarantee that every function will be compiled.

Use a normal, non-debug run when measuring performance. Debugging uses the VM. A bytecode cache affects compilation time rather than the steady-state cost of the script. For a useful comparison, keep the workload, process lifetime, cache state, and selected backend consistent, and account for warm-up before recording results.

## Watch mode

`--watch` re-runs the script when a source file or related module changes. `--watch-once` enables watch mode and exits after the first non-zero run result. Check mode, evaluation, the REPL, debugging, and package files cannot be combined with watch mode; a built package does not support `--watch`.

## Debugging

DAP over standard input and output:

```powershell
veroscript --debug hello.vs
```

DAP over TCP:

```powershell
veroscript --debug --dap-port=4711 hello.vs
veroscript --debug --dap-port=4711 --dap-bind=127.0.0.1 hello.vs
```

`--dap-port` accepts a value from `1` to `65535`; `--dap-bind` selects the listening address, defaults to `127.0.0.1`, and requires `--debug --dap-port`. In debug mode, DAP `launch` or `attach` supplies the program and its arguments; a command-line script path pre-seeds the program, and any trailing command-line arguments become the default script arguments for that request. `veroscript-dap` is a thin alias for the same debug host. See [Debugging](../../../../../VeroScriptTooling/Resources/Docs/User/en-US/debugging.md) for the full protocol boundary.

## Packages, AOT, and catalogs

Build application and library packages with `--emit-package`. `--package-file` can add source modules repeatedly, `--package-version` sets an unsigned package version, and `--strip-package-debug` removes source-file and line-table information. These options cannot be combined with `-e`, `-i`, `--check`, watch mode, or debugging. See [Packages and distribution](packages.md).

The `aot` subcommand requires a source script. The default target is C++17 and
uses `-o`/`--output` to emit a translation unit. Use `--target=python` to emit
standalone Python 3.11-3.15 source, or `--target=csharp` to emit C# source for
.NET 8/9. Python and C# support `--output-dir` and `--bundle-name` for source
bundles; `--manifest` is available for C# bundle output. The result is source,
not a linked executable. See [C++ AOT](../../../../../Extensions/Language/Cpp/Resources/Docs/User/en-US/aot.md), [Python AOT](../../../../../Extensions/Language/Python/Resources/Docs/User/en-US/aot.md),
and [C# AOT](../../../../../Extensions/Language/CSharp/Resources/Docs/User/en-US/aot.md).

`bindings validate` checks a catalog, while `bindings format` normalizes it; the latter can use `-o`/`--output` to write a new file. See [Host bindings](../../../../../Extensions/Language/Cpp/Resources/Docs/User/en-US/bindings.md).

## Diagnostics and environment variables

```powershell
veroscript --lang en-US --check script.vs
veroscript --version
```

Common environment variables include:

| Variable | Purpose |
| --- | --- |
| `VERO_PATH` | Module search paths; `;` on Windows and `:` on Unix. |
| `VERO_STDLIB_PATH` | Standard-library search roots. |
| `VERO_CACHE_DIR` | Bytecode-cache directory. |
| `VERO_LANG` | Diagnostic language such as any canonical BCP 47 tag loaded from the current catalog root. |
| `VERO_LOCALIZATION_DIR` | Localization catalog root. |
| `VERO_MAX_CALL_DEPTH` | Total recursion call-depth limit. |

Command-line options override the corresponding environment settings. An unsupported system or `VERO_LANG` locale falls back to English; an explicitly unsupported `--lang` value is rejected as an argument error. Use `veroscript --version` to inspect the installed version.

Localization roots use the `localization/<culture>/<component>.json` layout. See [Diagnostic localization](../../../../../VeroScript/Resources/Docs/User/en-US/localization.md) for validation, search order, and module-level catalogs.

## Unicode paths and arguments

On Windows, the CLI receives Unicode process arguments and converts them to UTF-8 before dispatch. Non-ASCII script paths, imported module paths and arguments passed to `main(string[] args)` therefore retain their text. Source files and localization JSON use UTF-8; tools reading redirected stdout or stderr should decode those streams as UTF-8.

## Backend selection

<a id="cli-backend-policy"></a>

`vm`, `mixed` and `jit` select execution policy, independently of JIT backend selection. Runtime does not bundle JIT. With an installed module environment, omitting `--jit-backend` inherits `services.jit.backend`; an unset choice defaults to `auto`, which tries enabled candidates in ascending backend-ID order and selects the first compatible usable backend. `--jit-backend=auto` overrides configuration; `--jit-backend=none` disables JIT. A backend ID, library file or directory may also be selected explicitly; an invalid explicit selection reports an error. `auto` also reports invalid candidate IDs or conflicting active providers for the same backend ID. Automatic selection requires a module environment. If JIT is disabled or automatic selection finds no usable backend, `mixed` uses VM and forced `jit` fails before execution. Put CLI options before the script path. Debugging uses the VM. Unsupported code may fall back before entry; a failure after entry never replays side effects.

Unified automatic, explicit and disabled selection rules are documented in [Service backend selection](../../../../../VeroScript/Resources/Docs/User/en-US/introduction.md#backend-selection).

```sh
veroscript --vm-backend=auto --jit-backend=auto main.vs
veroscript --jit-backend=none --backend=mixed main.vs
```

```text
veroscript --jit-backend="/path/to/Jit" --backend=mixed main.vs
```

## Script compilation extensions

See [Script compilation extensions](../../../../../VeroScript/Resources/Docs/User/en-US/standard-library/compiler.md#source-extension-activation).

<a id="cli-compiler-options"></a>

`--compiler-config <key=value>` adds one string configuration entry; repeat it for different keys. Values are not parsed as JSON and duplicate keys are rejected; --compiler-instructions and --compiler-timeout bound extension work; --no-compiler-imports disables source activation while configured extensions remain available. Extensions use the compile VM, with cooperative cancellation and restricted services; ordinary runtime imports grant no compilation authority. Generated code still obeys normal language rules. Standalone exports run generated business code rather than retaining an extension VM. See the Developer guide to author processors.

[Script compilation extensions](../../../../../VeroScript/Resources/Docs/User/en-US/standard-library/compiler.md)

The default total extension budget is 1,000,000 VM instructions and 2,000 ms. A zero value disables the corresponding budget; the limits do not preempt a blocking native callback.

`install -r <file>` / `install --requirement=<file>`: [Dependency-list files](../../../../../VeroScriptPackageManager/Resources/Docs/User/en-US/index.md).

## Native module commands

Commands supplied by an installed, enabled package with the native `cli` role are available directly in its selected project or component environment. Use the actual command and option names supplied by that package. Select another project with `--path <directory>` before module options.

For a local library, repeat `--cli-module <file>` as needed. Relative library paths use the startup directory; the loader accepts library files, not directory or PATH searches. Use `.dll` on Windows and the matching `.so`/`.dylib` on Linux/macOS. Put environment/backend options and library selectors before module options, then the command or script; subsequent arguments are forwarded unchanged.

Module command names take precedence over same-name files; use `./name` to run such a file. Built-in commands/options and duplicate registered names cannot be replaced. Module commands cannot combine with check, eval, REPL, watch, debug/DAP or bytecode-output modes. `--help` lists registered commands/options; `<command> --help` shows its usage without configuring or running it. Registration still loads the native module. Command output and descriptions come from the module; `--lang` supplies its callbacks with the selected language but does not automatically translate their text. Core CLI help and some validation messages remain in English.

```text
veroscript my-command arg
veroscript --path ./project --my-option=value my-command arg
veroscript --cli-module ./my-cli-module.dll --my-option=value my-command arg
veroscript --cli-module ./my-cli-module.dll my-command --help
```
