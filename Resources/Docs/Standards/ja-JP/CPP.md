# C++ コーディング規約

適用範囲：[VeroScript 本プロジェクトの開発・貢献](README.md)。

本ファイルが現行 C++ 規約の正本です。**推奨**または**必要に応じて**と明示した場合を除き、書式と構造の規則は必須です。

## 1. 字下げ、スコープ、波括弧

- 論理階層ごとに一つの Tab を使います。名前空間、型、メソッド、条件、ループ、lambda、局所スコープはそれぞれ一段深くします。
- 開始波括弧は単独行に置き、対応する宣言や制御文と揃えます。

  ```cpp
  void Process(const FRequest& Request)
  {
  	if (Request.bEnabled)
  	{
  		Execute(Request);
  	}
  }
  ```

- 開始直後や終了直前の空行は必須ではありません。空行は異なる論理区画を分けるためだけに使います。
- 終了波括弧は開始波括弧と揃えます。`else`、`else if`、`catch`、`do` 末尾の `while` は改行し、対応する終了波括弧と揃えます。節の開始波括弧も独立行に置きます。

  ```cpp
  if (bPrimary)
  {
  	HandlePrimary();
  }
  else
  {
  	HandleFallback();
  }
  ```

- 本体のある制御分岐には波括弧と独立スコープが必要です。`if`、`else`、`for`、`while`、`do`、範囲 `for`、各 `switch case` を含みます。
- 波括弧を省略できる唯一の分岐は、**本体が一つの直接的な `return` だけの一行ガード**です。

  ```cpp
  if (!bInitialized) return;
  ```

例外は `return;` または `return <式>;` だけです。`else` の連鎖、解放、ログ、代入、マクロ条件、入れ子の論理と組み合わせません。`break`、`continue`、`throw`、`co_return`、複数文の分岐は例外ではなく、波括弧付きスコープが必要です。

## 2. 型全体の配置

次の順に配置します。内容のない空区画は書きません。

1. 必要に応じて型の先頭に `friend`、`using`、`typedef` などの関係・別名；
2. `DECLARE_XXX` など必要なマクロ；
3. `public`、`protected`、`private` の固定順のアクセス領域；
4. 各領域で継承した `override` メソッドを先に；
5. 内部型；
6. この型独自のメソッド；
7. 最後にメンバー変数。

推奨する骨格：

```cpp
class FExample : public IBase, protected ISecondary
{
	friend class FExampleFactory;
	using FBase = IBase;

	DECLARE_EXAMPLE_TYPE(FExample)

public:
	//~ Begin IBase Interface
	virtual void Initialize() override;
	virtual void Shutdown() override;
	//~ End IBase Interface

	enum class EState
	{
		Idle,
		Running,
	};

	struct FOptions
	{
		bool bEnabled = false;
	};

	void Start(const FOptions& Options);

protected:
	//~ Begin ISecondary Interface
	virtual bool CanStart() const override;
	//~ End ISecondary Interface

	void NotifyStarted();

private:
	void ResetState();

	EState State = EState::Idle;
	FOptions Options;
};
```

### 2.1 アクセス領域

- `public`、`protected`、`private` の順を守ります。
- 同じアクセスレベルは可能なら一つの連続領域にまとめます。言語、マクロ展開、明確な意味の境界が必要とする場合だけ指定子を繰り返し、全体の順序を崩しません。
- メンバー変数は実際のアクセス領域の末尾に置き、メソッドや内部型の間に挟みません。

### 2.2 継承メソッド

- 各アクセス領域では `override` をこの型の新規メソッドより先に置きます。
- 基底が複数なら継承リストの左から右の順に分け、同じ基底の中はそのインターフェースの宣言順にします。
- 継承メソッドが複数、基底が分かりにくい、または独自メソッドと隣接して紛らわしい場合は対の標識を使います。

  ```cpp
  //~ Begin ISerializable Interface
  virtual bool Serialize(FArchive& Archive) override;
  virtual bool Deserialize(FArchive& Archive) override;
  //~ End ISerializable Interface
  ```

- `Begin` と `End` は対にし、直接の基底またはインターフェース名を完全に一致させます。一つの明白な `override` では必要に応じて省略し、すべての関数に機械的に追加しません。

### 2.3 内部型

同じアクセス領域の固定優先順は次のとおりです。

1. `enum`、`enum class`；
2. `struct`；
3. `union`、局所別名、関数オブジェクト型など他の型宣言；
4. `class`。

- 型の区分間は一行空けます。同じ種類は依存と名前に基づく読みやすい順にします。
- 型の先頭に置く通常の `using`、`typedef` を理由なく内部型領域へ残しません。先行する内部型に依存する別名だけを「他の型宣言」の位置に置きます。
- 完全定義の依存が順序と競合する場合は、まず前方宣言で解決します。避けられない場合は、完全型の依存理由を近くに説明します。

## 3. ヘッダー、前方宣言、実装ファイル

### 3.1 ヘッダーと必要に応じた実装ファイル

- 所有する C++ `.h` の先頭は、著作権とライセンスを示す 2 行の SPDX ヘッダー、空行、`#pragma once`、空行、include または他の宣言の順です。

  ```cpp
  // SPDX-FileCopyrightText: <copyright-holder>
  // SPDX-License-Identifier: MIT

  #pragma once

  #include <cstdint>
  ```

- `.inl` は取り込む実装断片であり `.h` とは異なります。著作権とライセンスを示す 2 行の SPDX ヘッダーと空行で始めますが、通常は `#pragma once` も対応 `.cpp` も不要です。翻訳単位につき一度だけ取り込むヘッダー相当の内容と確認した場合に限り、`.h` と同じ扱いで `#pragma once` を使います。
- `.h` に同名 stem の `.cpp` を必須としません。実装またはビルド上の責務が独立した翻訳単位を必要とする場合だけ、責務に応じて `.cpp` を設けます。ファイル数やディレクトリの対称性のために空実装ファイルを作りません。
- 宣言、型定義、定数、テンプレート、`inline` 定義だけのヘッダーは単独で存在できます。ヘッダー内で可視である必要がある定義は、ファイル分割のために移動しません。
- `.cpp` が必要なら同じモジュールの実装領域に配置し、実装するヘッダーを明示的に include します。`Public/`・`Private/` 分離がなければ通常は同じディレクトリ、分離があれば `Private/` の適切な意味上のサブディレクトリに置き、`Public/` と同じ相対パスを要求しません。
- 実装専用 `.cpp` に同名 `.h` がなくても構いません。
- 既存の空 `.cpp` を削除する際は、実際のビルド、登録、明示的インスタンス化、プラットフォーム上の責務を確認し、ビルド参照も同時に更新します。
- 第三者・生成ファイルはそれぞれに適用されるファイル構成を保持します。

### 3.2 宣言と定義の順序

- `.h` で宣言し `.cpp` に実装するメソッドは、宣言順に定義します。
- 継承インターフェース実装、独自の公開・保護・非公開メソッドの区分と相対順序も保持します。
- 無名名前空間の補助関数、ファイル局所定数、実装専用型は定義より前に配置できますが、ヘッダー宣言に対応する定義の相対順は変えません。
- 宣言を追加したら `.cpp` の定義位置も確認し、実装を一律に末尾へ追加しません。

### 3.3 前方宣言と複数のトップレベル型

- すべての前方宣言は `enum` → `struct` → その他 → `class` の順です。
- `enum` の前方宣言には有効な opaque-enum 形式を使います。`enum class EName;` または基礎型を明示した `enum EName : std::uint8_t;` です。基礎型なしの非スコープ `enum EName;` は宣言しません。
- 同じヘッダーに複数のトップレベル型を定義できます。完全型の依存が許す範囲で `enum` → `struct` → その他 → `class` の順にします。
- 「その他」には `union`、`using`/`typedef` の別名、関数型の別名を含みます。クラステンプレートは `class`、構造体テンプレートは `struct` に分類し、すべての `template` をその他へまとめません。
- 完全型の依存で別の順が必要なら、まず前方宣言を試します。避けられなければ依存を優先し、近くに短く理由を書きます。

### 3.4 メンバーの既定値と真偽値ビットフィールド

- 初期値が必要で、既定状態を宣言箇所に直接明確に表せる場合は、その場所で既定値を与えます。
- コンストラクター引数、実行時状態、他のメンバー初期化結果に依存する値は初期化リストに置きます。規則のために誤解を招く固定値を付けません。
- アドレス取得、参照、アトミック操作、安定した外部バイナリ配置を必要とせず、圧縮格納に適した真偽値のスイッチには 1 ビットのフィールドを優先します。例は `uint8 bEnabled : 1;` または `std::uint8_t bEnabled : 1;` です。幅は `: 1`、`uint8` は格納型です。
- 現在の最低標準は C++17 です。C++17 のビットフィールドはクラス内既定メンバー初期化を使えません。非ゼロまたは明示的な初期状態が必要ならコンストラクター初期化リストで設定します。対応標準へ変更する前に `uint8 bEnabled : 1 = true;` と書きません。

## 4. `switch` と実行分岐

- すべての `switch` に `default` が必要です。
- `case` と `default` は `switch` 内容の階層に揃え、実行本体の波括弧を一段、本体の文をさらに一段字下げします。

```cpp
switch (Kind)
{
case EKind::First:
	{
		HandleFirst();
		break;
	}
case EKind::Second:
	{
		HandleSecond();
		break;
	}
default:
	{
		HandleUnknown();
		break;
	}
}
```

- 唯一の経路が `return` または `return <式>` で直接メソッドを終了する `case` は、1 節の一行ガード例外を使えます。ログ、解放、局所宣言、条件、その他の文を混在させません。他の `case` と `default` はすべて上記の独立スコープを使います。
- 業務上の処理がない `default` にも波括弧と明示的な `break` を残します。何もしない理由が文脈で明白でない場合だけ、短い英語コメントで説明します。
- 暗黙の fallthrough に依存しません。意図的な貫通はプロジェクトが認める明示的な標識で示し、理由を説明します。
- 1 節で厳密に定義した直接 `return` のガード以外は、すべての実行分岐に波括弧を使います。

## 5. プリプロセッサーマクロ

- `#if`、`#ifdef`、`#ifndef`、`#elif`、`#else`、`#endif` は、囲むコードと**同じ論理階層**に字下げします。プリプロセッサー条件で一段増やしません。
- 条件を除いてもコードの階層と読みやすさが変わらないようにします。

  ```cpp
  void Initialize()
  {
  	#if WITH_DIAGNOSTICS
  	RegisterDiagnostics();
  	#endif

  	StartRuntime();
  }
  ```

- 条件マクロは可能な限り意味上の区画全体を囲み、一つの宣言や式を読みにくい断片へ分割しません。
- 対になるマクロの字下げを一致させます。長い区画の `#endif` には必要に応じて条件を短くコメントします。
- マクロ生成宣言も本規約の型配置順に置きます。

## 6. コメントと領域

- 一行の説明は `//` で宣言や区画のすぐ上に置きます。行末の短いコメントは読みやすさを妨げない場合だけ使います。
- 複数行の API の意味、所有権、スレッド、失敗条件、複雑な不変条件には `/** ... */` 文書コメントを使います。
- `GetName()` の前の `// Gets the name` のように、自明な名前を繰り返しません。
- メンバー変数の説明では、単位、所有権、有効期間、スレッド制約、キャッシュ無効化条件、他フィールドとの関係を優先します。
- `//~ Begin <Name> Interface` / `//~ End <Name> Interface` は継承インターフェースの区画だけに使い、通常メソッドの見出しに流用しません。
- 他の大きな区画には短い説明を付けられますが、固定配置によって構造自体を明確にすることを優先します。

## 7. その他の推奨

- `.cpp` と `.h` の include 順・分類は現在指定しません。ファイルの読みやすさとビルド制約に従います。前方宣言は引き続き 3.3 節に従います。
- null ポインターには `nullptr` を使い、情報を失う可能性のある変換は明示します。
- 資源所有権、null になりうるオブジェクト、スレッド間コールバックは型・メソッドコメントで明確に説明します。
- 空関数、既定実装、意図的に無視する引数は最短で読みやすく表します。形式のためだけに不要な局所変数や空スコープを作りません。

## 8. 保守者が補足する事項

命名の詳細、テンプレート・concept、例外方針、スマートポインター方針、テストフレームワーク、整形ツール、行幅はまだ必須規則になっていません。保守者の決定後に補います。include 順は現時点で明示的に指定しません。
