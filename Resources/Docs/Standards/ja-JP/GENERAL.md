# 共通コーディング規約

適用範囲：[VeroScript 本プロジェクトの開発・貢献](README.md)。

全言語に共通する規則だけを記載します。言語固有の字下げ、波括弧、型配置、構文は各言語の規約に従います。

## 構造と階層

- 責務ごとにコードを分けます。一つの区画は、継承インターフェース、内部型、公開メソッド、非公開補助メソッド、メンバーデータなど、容易に名前を付けられる一つの概念を表します。
- 区画の間は一行空けます。連続した空行、長い区切り線、意味のない領域名で明確な構造を代替しません。
- スコープ、名前空間、型、メソッド、条件、ループの入れ子は実際の階層を示します。行数を減らすために階層を潰しません。
- 規則が未定義なら、変更の中で新しい書式を導入するより、近くの一貫した既存書式を優先します。

## 字下げ

- 所有する手動保守のソース、テスト、サンプル、ビルド/ツールスクリプトは、論理階層ごとに実際の Tab を一つ使い、既定の表示幅を 4 桁とします。階層の字下げを空白だけで代用しません。
- Tab は階層を表します。継続行の桁合わせには言語構文が許す位置で空白を使えますが、ブロックの字下げとして両者を混在させません。
- 言語とファイル形式の構文を優先します。[YAML の階層の字下げには空白が必要](https://yaml.org/spec/1.2.2/#61-indentation-spaces)であり、明示的な例外です。Python の解析規則は [PYTHON.md](PYTHON.md) を参照します。
- Markdown の文書構造を保持し、コードブロックは各言語の規約に従います。文字列、テスト入力、第三者原文、生成結果は機械的に変換せず、生成ソースの書式は担当テンプレートで必要に応じて調整します。

## ファイルの改行コード

- 本リポジトリ所有のテキストファイルは LF（`\n`）を使用します。ソース、テストコード、サンプル、文書、設定、ビルド/ツールスクリプトを含み、Windows、Linux、macOS のチェックアウトと編集で同じ規則を適用します。Tab による字下げの規則は変えません。
- `.editorconfig` と `.gitattributes` を一致させます。リポジトリ内のファイルを保守する生成ツールも LF を明示的に使用します。実際の行末だけを変換し、文字コードと BOM、特に Windows PowerShell 5.1 が必要とする UTF-8 BOM を保持します。`\r\n` エスケープ、プロトコル区切り、利用者入力、リテラルデータは書き換えず、言語やツールの CRLF 入力への対応も縮小しません。
- 第三者の原文、外部から導入したライセンス/ビルドツールのファイル、バイナリ資源、バイト列に依存するフィクスチャは機械的に変換しません。内容と、固有または既存の Git 改行規則を保持します。本プロジェクトが記述したライセンス案内は LF を使用します。Tests ディレクトリにあるという理由だけで通常のテストコードを除外しません。
- Windows の `.bat` と `.cmd` ランチャーは CRLF を使用します。それ以外の複数行リテラルやフィクスチャが物理的な改行値に依存する場合は既存のバイト列を保持し、根拠のある例外を具体的なパスで Git とエディタ設定に記録します。元の改行への依存がなくなったことを確認してから例外を解除します。LF 規則のためにテスト入力、出力内容、実行動作を変更しません。

## 命名

- 名前は責務、状態、値を説明します。`New`、`Old`、`Temp`、`Final`、`v2` など段階だけを示す名前は使いません。
- 同じモジュール内の同じ概念には一つの安定した名前を使います。言語境界のプロトコル名は契約の綴りを維持します。
- 真偽値の名前は肯定的な意味を表し、条件を直接読めるようにします。
- 新しい略語は局所的な文脈で理解可能にします。既存の公開略語の大文字・小文字と綴りは統一します。

## コメント

- 所有する手動保守ソースのコメントはすべて英語にします。行、ブロック、文書、領域コメントを含みます。外部プロトコルの原文引用、第三者ライセンス、生成内容はこの規則による翻訳の対象外です。
- **理由**、不変条件、境界、所有権、スレッド要件、互換性、自明でない選択を説明します。明らかなコードを一行ずつ言い換えません。
- 型、メンバーメソッド、メンバー変数には必要に応じて説明を付けます。公開部分、複雑な状態、資源所有権、誤用しやすいインターフェースを優先し、名前で十分伝わる単純なメンバーに重複説明を付けません。
- 一行の説明は慣用的な行コメントを使います。例は C 系の `//`、Python の `#` です。連続する説明、引数・戻り値の意味、整形された文書には、その言語の文書コメントを使います。
- 複数行ブロックコメントは、まとめて読む必要のある説明、ライセンス、埋め込みテキストに限ります。通常のコードを囲みません。
- 説明対象のコードに隣接させ、コード変更時に古いコメントを更新または削除します。

## ファイル先頭の著作権表示

以下の表示テンプレートは、該当する著作権帰属を持つ本プロジェクト内のコードにのみ使用します。正確な著作権者はルートの `LICENSE` を参照します。外部プロジェクトは自分のコードの実際の権利者を記載します。本プロジェクトのコードを複製・配布する際は、適用されるライセンスに従い既存の著作権表示とライセンス全文を引き続き保持します。

- 所有する手動保守のソース、テスト、サンプル、ビルド/ツールスクリプトのうち MIT ライセンスのものは、次の 2 行の SPDX ヘッダーを使用します。新規ファイルに追加し、既存のプロジェクト独自の表示は一括移行または関連する変更の際に新形式へ置き換えます。
- 使用前にテンプレートの `<copyright-holder>` を、ルートの `LICENSE` に記載された正確な著作権者に置き換えます。ソースヘッダーには年と URL を記載しません。2 行の順序を固定し、フィールド名、著作権者、ライセンス識別子は翻訳しません。
- C 系言語、C#、VeroScript、TypeScript/JavaScript、Java、Kotlin は `//` を使います。

```cpp
// SPDX-FileCopyrightText: <copyright-holder>
// SPDX-License-Identifier: MIT
```

- Python、CMake、PowerShell、Shell スクリプトは `#` を使います。

```python
# SPDX-FileCopyrightText: <copyright-holder>
# SPDX-License-Identifier: MIT
```

- XML、XAML、Avalonia `.axaml` のソースは、別々の 2 行の XML コメントを使います。

```xml
<!-- SPDX-FileCopyrightText: <copyright-holder> -->
<!-- SPDX-License-Identifier: MIT -->
```

- 最初の通常ソース行より前に置き、ヘッダーの後は一行空けます。shebang、文字コード宣言、PowerShell `#requires`、XML 宣言など位置が指定される指示は先頭に保持し、その後に 2 行を置きます。
- 生成ソースと型宣言には、必要に応じて担当の生成テンプレートからヘッダーを出力します。書式だけのために生成結果を手作業で変更しません。
- 第三者または外部から取り込んだコードの著作権表示とライセンス表示は保持します。本プロジェクトの名前や MIT 識別子へ一括置換しません。
- Markdown 文書、JSON/YAML 設定、画像などの資源には、ファイルごとのコードヘッダーを要求しません。
- SPDX の 2 行はライセンス全文の代わりにはなりません。ルートの `LICENSE` に著作権年と MIT 全文を保持し、元の著作権者を保持します。配布物にはライセンスが要求する著作権表示と許諾文を完全な形で保持します。

## 改行と読みやすさ

- 改行は意味上の階層、引数の区分、読む順序のために使い、機械的な行幅合わせにしません。
- 長い引数、テンプレート引数、初期化子、条件は論理単位で改行し、継続行が同じ式に属すると分かるようにします。
- すべての開始波括弧の直後や終了波括弧の直前に空行を要求しません。最初・最後の論理区画に応じて判断します。
- 一行には一つの主要な意図を載せます。単純なガード、空関数、慣用的な省略の例外は言語規約の明示的な規定に従い、未規定なら省略しません。
- 言語が対応する構文を持つ場合、`else`、`else if`（PowerShell は `elseif`）、`catch`、`finally`、`do…while` 末尾の `while` は改行し、直前の終了波括弧と揃えます。
  `} else` のような同一行の記述は禁止です。
  節がブロック本体を持つ場合、開始波括弧も独立行で節に揃え、本体の文と終了波括弧も別の行に置きます。
  整形のためだけに文字列、テスト入力、第三者の原文を機械的に変更せず、マクロでは行継続の意味を保ちます。

- フォーマッター、ソースコード生成テンプレート、現行ドキュメントの例もこの節の配置に従います。テスト入力の本来の検証目的は保持します。

```cpp
if (bPrimary)
{
	HandlePrimary();
}
else
{
	HandleFallback();
}
```

## 変更原則

- 現在の作業に必要な内容だけを変更し、無関係なユーザー変更を削除、上書き、並べ替えしません。
- 振る舞い、公開インターフェース、シリアライズ形式、言語境界が変わる場合は、宣言、実装、呼び出し側、テストを同時に更新します。
- 拒否、回復、フォールバックは呼び出し側から観測可能にし、失敗を成功に見せかけません。
- 外部入力、ファイルパス、プロセス引数、資源の寿命は、それを所有する境界で検証・解放します。


## エディタと組み込みプラットフォーム

Core は言語意味、実行サービス、汎用 VM/JIT 契約を管理します。バイトコードの命令ループは `Modules/Execution/VeroScriptBytecodeVm`、具体的な JIT コンパイル、IR、ネイティブ生成、外部依存は `Modules/Execution` に属します。公開契約を使い、インスタンス、ワーカー、保持コードの存続中はモジュール所有を保持します。ファクトリー前に ABI を検証し、選択失敗時は旧バックエンドを維持します。実行中はバックエンドの選択や設定を変更しません。

エディタは設定とプロトコル表示を管理します。Mobile/Android/iOS は公開 C ABI を使いリソースを明示提供し、実際のプラットフォーム検証を記録します。作成スレッド、コールバック寿命、取消/reset を守り、割当量を完全な sandbox と説明しません。Kotlin/Java の命名と構造はモジュール慣例に従い、字下げは本書の共通規則に統一します。Objective-C/Objective-C++ はプラットフォーム所有規則とネイティブ境界に従います。プロトコル識別子は安定させます。

User は操作、可観測動作、公開 API、Developer は構造、ビルド、検証、出版を扱い、過去の版と環境の検証記録はバージョン管理または無視対象の証拠に保存し、出版文書には含めません。変更時は六言語を更新し、UI 検証と診断を catalog で翻訳して ID、キー、引数を保持します。リンクと All/User 出版を検証し、スキップしたプラットフォーム/IDE テストで発行認定を主張しません。
