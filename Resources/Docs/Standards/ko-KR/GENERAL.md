# 공통 코딩 규칙

적용 범위: [VeroScript 프로젝트 개발 및 기여](README.md).

모든 언어에 공통인 규칙만 기록합니다. 언어별 들여쓰기, 중괄호, 타입 배치 및 구문은 각 언어 규칙을 따릅니다.

## 구조와 계층

- 책임에 따라 코드를 나눕니다. 한 구역은 상속 인터페이스, 내부 타입, 공개 메서드, 비공개 보조 메서드, 멤버 데이터처럼 이름을 붙이기 쉬운 한 개념만 표현합니다.
- 구역 사이에 빈 줄 하나를 둡니다. 연속 빈 줄, 긴 구분선, 의미 없는 영역 제목으로 명확한 구조를 대신하지 않습니다.
- 범위, 네임스페이스, 타입, 메서드, 조건 및 루프는 실제 중첩 계층을 나타내야 합니다. 줄 수를 줄이기 위해 계층을 평탄화하지 않습니다.
- 정의되지 않은 규칙은 한 변경에서 새 스타일을 도입하기보다 가장 가까운 기존의 일관된 방식을 우선합니다.

## 들여쓰기

- 프로젝트가 소유하고 수동으로 관리하는 소스, 테스트, 예제 및 빌드/도구 스크립트는 논리 계층마다 실제 Tab 하나를 사용하며 기본 표시 너비는 네 칸입니다. 계층 들여쓰기를 공백만으로 대체하지 않습니다.
- Tab은 계층을 나타냅니다. 이어지는 줄은 언어 구문이 허용하는 위치에서 정렬용 공백을 사용할 수 있지만 블록의 계층 들여쓰기로 둘을 섞지 않습니다.
- 언어와 파일 형식의 구문을 우선합니다. [YAML은 계층 들여쓰기에 공백이 필요](https://yaml.org/spec/1.2.2/#61-indentation-spaces)하므로 명시적 예외입니다. Python의 해석 규칙은 [PYTHON.md](PYTHON.md)를 따릅니다.
- Markdown 문서 구조를 유지하고 코드 블록은 해당 언어 규칙을 따릅니다. 문자열, 테스트 입력, 타사 원문 및 생성 결과를 기계적으로 변환하지 않으며 생성 소스의 형식은 해당 템플릿에서 필요에 따라 조정합니다.

## 파일 줄 끝 형식

- 저장소가 소유한 텍스트 파일은 LF(`\n`)를 사용합니다. 소스, 테스트 코드, 예제, 문서, 설정 및 빌드/도구 스크립트를 포함하며 Windows, Linux, macOS의 체크아웃과 편집에 같은 규칙을 적용합니다. Tab 들여쓰기 규칙은 바꾸지 않습니다.
- `.editorconfig`와 `.gitattributes`를 일치시킵니다. 저장소 파일을 관리하는 생성 도구도 LF를 명시적으로 사용합니다. 실제 줄 끝만 변환하고 인코딩과 BOM, 특히 Windows PowerShell 5.1에 필요한 UTF-8 BOM을 보존합니다. `\r\n` 이스케이프, 프로토콜 구분자, 사용자 입력 또는 리터럴 데이터를 바꾸지 않으며 언어나 도구의 CRLF 입력 지원도 줄이지 않습니다.
- 타사 원문, 외부에서 가져온 라이선스/빌드 도구 파일, 바이너리 리소스 및 바이트에 민감한 테스트 입력은 기계적으로 변환하지 않습니다. 내용과 자체 또는 기존 Git 줄 끝 정책을 유지합니다. 프로젝트에서 작성한 라이선스 안내는 LF를 사용합니다. Tests 디렉터리에 있다는 이유만으로 일반 테스트 코드를 제외하지 않습니다.
- Windows `.bat`, `.cmd` 실행 스크립트는 CRLF를 사용합니다. 그 밖에 실제 줄 끝 값에 의존하는 여러 줄 리터럴이나 테스트 입력은 기존 바이트를 보존하고 근거가 있는 예외를 Git과 편집기 설정에 정확한 경로로 기록합니다. 원래 줄 끝에 더 이상 의존하지 않음을 확인한 뒤 예외를 제거합니다. LF 규칙을 맞추려고 테스트 입력, 출력 내용 또는 실행 동작을 바꾸지 않습니다.

## 이름

- 이름은 책임, 상태 또는 값을 설명해야 합니다. `New`, `Old`, `Temp`, `Final`, `v2` 같은 단계별 임시 이름을 사용하지 않습니다.
- 같은 모듈의 같은 개념에는 안정적인 이름 하나만 사용합니다. 언어 경계의 프로토콜 이름은 계약된 철자를 유지합니다.
- 불리언 이름은 긍정 의미를 표현하여 조건을 바로 읽을 수 있게 합니다.
- 새 약어는 국소 문맥에서 이해할 수 있어야 합니다. 기존 공개 약어의 대소문자와 철자를 일관되게 유지합니다.

## 주석

- 직접 소유하고 수동 관리하는 소스의 모든 주석은 영어로 작성합니다. 한 줄, 블록, 문서 및 영역 주석을 포함합니다. 외부 프로토콜 원문, 외부 라이선스 및 생성 내용은 이 규칙에 따라 번역하지 않습니다.
- **이유**, 불변 조건, 경계, 소유권, 스레드 요구, 호환성 또는 명확하지 않은 선택을 설명합니다. 명백한 코드를 한 줄씩 되풀이하지 않습니다.
- 타입, 멤버 메서드와 멤버 변수에 필요에 따라 주석을 추가합니다. 공개 표면, 복잡한 상태, 자원 소유권, 오용하기 쉬운 인터페이스를 우선하며 이름으로 충분한 단순 멤버에 중복 설명을 달지 않습니다.
- 한 줄 설명은 언어 관용 구문을 사용합니다. C 계열의 `//`, Python의 `#`가 예입니다. 연속 설명, 매개변수·반환 의미, 형식화된 문서는 언어의 관용 문서 주석을 사용합니다.
- 여러 줄 블록 주석은 함께 읽어야 하는 설명, 라이선스 또는 삽입 텍스트에만 사용하고 일반 코드를 감싸지 않습니다.
- 주석을 설명 대상 코드에 인접하게 두고 코드 변경 시 오래된 주석을 수정하거나 삭제합니다.

## 파일 머리 저작권 문구

아래 문구 템플릿은 해당 저작권 귀속이 있는 이 프로젝트의 코드에만 사용합니다. 정확한 권리자는 루트 `LICENSE`를 참조합니다. 외부 프로젝트는 자기 코드의 실제 권리자를 표시합니다. 이 프로젝트의 코드를 복사하거나 배포할 때는 해당 라이선스에 따라 기존 저작권 문구와 라이선스 전문을 계속 보존해야 합니다.

- 프로젝트가 소유하고 수동으로 관리하며 MIT 라이선스를 적용하는 소스, 테스트, 예제 및 빌드/도구 스크립트는 아래 두 줄 SPDX 머리 문구를 사용합니다. 새 파일에 추가하고, 기존 자체 문구는 일괄 이전이나 관련 수정 시 새 형식으로 교체합니다.
- 사용 전에 템플릿의 `<copyright-holder>`를 루트 `LICENSE`에 기록된 정확한 권리자로 바꿉니다. 소스 파일 머리에 연도와 URL을 넣지 않습니다. 두 줄의 순서를 유지하고 필드 이름, 저작권자 및 라이선스 식별자는 번역하지 않습니다.
- C 계열 언어, C#, VeroScript, TypeScript/JavaScript, Java 및 Kotlin은 `//`를 사용합니다.

```cpp
// SPDX-FileCopyrightText: <copyright-holder>
// SPDX-License-Identifier: MIT
```

- Python, CMake, PowerShell 및 Shell 스크립트는 `#`를 사용합니다.

```python
# SPDX-FileCopyrightText: <copyright-holder>
# SPDX-License-Identifier: MIT
```

- XML, XAML 및 Avalonia `.axaml` 소스는 별도의 두 줄 XML 주석을 사용합니다.

```xml
<!-- SPDX-FileCopyrightText: <copyright-holder> -->
<!-- SPDX-License-Identifier: MIT -->
```

- 첫 일반 소스 줄보다 앞에 두고 문구 뒤에 빈 줄 하나를 둡니다. shebang, 인코딩 선언, PowerShell `#requires`, XML 선언처럼 위치가 지정된 지시문은 먼저 유지하고 그 뒤에 두 줄을 둡니다.
- 생성 소스와 타입 선언의 문구는 필요에 따라 해당 생성 템플릿에서 출력합니다. 머리 형식만 맞추기 위해 생성 결과를 직접 수정하지 않습니다.
- 타사 또는 외부에서 가져온 코드의 저작권 및 라이선스 문구를 보존합니다. 프로젝트 이름이나 MIT 식별자로 일괄 교체하지 않습니다.
- Markdown 문서, JSON/YAML 설정, 이미지 및 기타 리소스에는 파일마다 코드 머리 문구를 요구하지 않습니다.
- SPDX 두 줄은 전체 라이선스 본문을 대신하지 않습니다. 루트 `LICENSE`에 저작권 연도와 전체 MIT 본문을 유지하고 원래 권리자를 유지합니다. 배포물에는 라이선스가 요구하는 전체 저작권 및 허가 문구를 유지합니다.

## 줄바꿈과 가독성

- 줄바꿈은 의미 계층, 매개변수 그룹 및 읽기 방향을 위한 것이며 기계적인 줄 너비 맞추기가 아닙니다.
- 긴 매개변수, 템플릿 인수, 초기화자 또는 조건은 논리 단위로 나누고 이어지는 줄이 같은 표현식에 속함을 명확하게 합니다.
- 모든 여는 중괄호 뒤나 닫는 중괄호 앞에 빈 줄을 강제하지 않습니다. 첫 번째·마지막 논리 구역에 따라 결정합니다.
- 한 줄에는 주된 의도 하나만 담습니다. 단순 가드, 빈 함수, 관용 축약의 예외는 언어별 명시적 규칙에 따르며 규정이 없으면 축약하지 않습니다.
- 해당 구문을 지원하는 언어에서는 `else`, `else if`(PowerShell의 `elseif`), `catch`, `finally`, `do…while` 끝의 `while`을 새 줄에 두고 앞 블록의 닫는 중괄호에 맞춥니다. `} else`처럼 같은 줄에 쓰지 않습니다. 절에 블록 본문이 있으면 여는 중괄호도 절에 맞춘 독립된 줄에 두고, 본문 문장과 닫는 중괄호도 각각 별도 줄에 둡니다. 형식만 맞추려고 문자열, 테스트 입력 또는 타사 원문을 기계적으로 바꾸지 않으며 매크로의 줄 연속 의미를 보존합니다.

- 포매터, 소스 코드를 출력하는 생성 템플릿과 현행 문서 예제도 이 절 배치를 따릅니다. 테스트 입력의 원래 검증 목적은 유지합니다.

```cpp
if (bPrimary)
{
	HandlePrimary();
}
else
{
	HandleFallback();
}
```

## 변경 원칙

- 현재 작업에 필요한 내용만 바꾸며 무관한 사용자 변경을 삭제, 덮어쓰기 또는 재정렬하지 않습니다.
- 동작, 공개 인터페이스, 직렬화 또는 언어 경계가 변경되면 선언, 구현, 호출자와 테스트를 함께 갱신합니다.
- 거부, 복구 또는 대체 동작은 호출자가 관찰할 수 있어야 하며 실패를 성공처럼 표시하지 않습니다.
- 외부 입력, 파일 경로, 프로세스 인수 및 자원 수명은 소유하는 경계에서 검증하고 정리합니다.


## 에디터와 임베디드 플랫폼

Core는 언어 의미, 실행 서비스와 일반 VM/JIT 계약을 소유합니다. 바이트코드 명령 루프는 `Modules/Execution/VeroScriptBytecodeVm`, 구체적 JIT 컴파일, IR, 네이티브 생성과 외부 의존성은 `Modules/Execution`가 담당합니다. 공개 계약을 사용하고 인스턴스, worker, 보관 코드 동안 모듈 소유권을 유지합니다. 팩터리 전 ABI를 검증하고 선택 실패 시 이전 백엔드를 유지합니다. 실행 중에는 백엔드 선택이나 구성을 변경하지 않습니다.

에디터는 설정과 프로토콜 표시를 소유합니다. Mobile/Android/iOS는 공개 C ABI로 명시적 리소스를 제공하고 실제 플랫폼 검증을 기록합니다. 생성 스레드, 콜백 수명, 취소/reset 계약을 지키고 할당량을 완전한 sandbox로 설명하지 않습니다. Kotlin/Java의 이름과 구조는 모듈 관례를 따르며 들여쓰기는 이 문서의 공통 규칙으로 통일합니다. Objective-C/Objective-C++는 플랫폼 소유권과 네이티브 경계를 따릅니다. 프로토콜 식별자를 유지합니다.

User는 작업, 관찰 가능한 동작과 공개 API를, Developer는 구조, 빌드, 검증, 출판을 다루며 이전 버전과 환경별 검증 기록은 버전 관리나 무시된 증거에 보존하고 출판 문서에서는 제외합니다. 변경 시 여섯 언어를 갱신하고 UI 검증/진단을 catalog로 번역하되 ID, 키, 인수는 보존합니다. 링크와 All/User 출판을 검사하며 건너뛴 플랫폼/IDE 테스트로 출시 인증을 주장하지 않습니다.
